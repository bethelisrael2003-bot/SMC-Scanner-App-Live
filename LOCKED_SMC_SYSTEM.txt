========================================================================
PART A — WHAT THE SYSTEM ACTUALLY DOES
========================================================================

The background scanner runs every 60 seconds. Each cycle does two
things in order: (1) manage open trades, then (2) scan for new ones.


------------------------------------------------------------------------
A1. SESSION TIMING
------------------------------------------------------------------------

The scanner only generates new trades during these windows (GMT):

  Weekend (Saturday, Sunday before 21:00)     → NO TRADES
  Asian session (00:00–07:00)                → NO TRADES
  Monday first 4 hours (00:00–04:00)         → Can trade (flagged reduced)
  London Kill Zone (07:00–10:00)             → ACTIVE
  Midday (10:00–12:00)                       → ACTIVE
  London/NY Overlap (12:00–16:00)            → ACTIVE (best window)
  Late NY (16:00–21:00)                      → ACTIVE
  After 21:00                                → NO TRADES

Additionally: if any trade was closed by the volatility cooldown
(see A7) on a given day, no new trades open for the rest of that
calendar day (EOD lockout).


------------------------------------------------------------------------
A2. ENTRY REQUIREMENTS (ALL must pass)
------------------------------------------------------------------------

For a trade to open on a pair, every gate below must pass:

  GATE 1: SESSION
    Must be in an active Kill Zone window (see A1).
    Must not be in EOD lockout.

  GATE 2: RE-ENTRY COOLDOWN
    If pair already has an Open trade → skip.
    If pair's last trade closed < 30 minutes ago → skip.
    After 30 min: if new signal is same direction + entry price moved
    < 0.3% from last closed entry → block (same setup re-trigger).

  GATE 3: SPREAD (automated, uses real Capital.com bid/ask)
    Standard FX pairs: spread > 5 pips → WAIT
    Gold (XAU/USD):    spread > 50 pips → WAIT
    Silver (XAG/USD):  spread > 15 pips → WAIT

  GATE 4: H1 TREND
    H1 must show clear BULLISH (Higher Highs + Higher Lows) or
    BEARISH (Lower Highs + Lower Lows). RANGE or unclear → WAIT.

  GATE 5: DAILY ALIGNMENT
    Daily trend must either:
      • Match H1 trend (both bullish or both bearish), OR
      • Be RANGE itself (neutral — doesn't conflict)
    If Daily clearly opposes H1 → WAIT.

  GATE 6: PREMIUM / DISCOUNT
    Price must be in Premium (top 30% of 50-candle range) for SELL,
    or Discount (bottom 30%) for BUY. Middle 40% (EQ) → WAIT.
    Range must be ≥ 1.5× ATR(14) to be valid. Compressed → WAIT.

  GATE 7: TREND-ZONE MATCH
    Bullish trend must be in Discount. Bearish must be in Premium.
    Bullish in Premium → WAIT. Bearish in Discount → WAIT.

  GATE 8: POI (Order Block or FVG)
    Must find a valid Order Block (last opposing candle before a
    displacement move ≥ 1.5× ATR) or Fair Value Gap (3-candle
    imbalance). If POI is DEAD (price traded through with a strong
    body candle) → WAIT.

  GATE 9: M15 ENTRY CANDLE
    The most recent M15 candle must confirm entry direction via ONE of:
      • Strong body ≥ 60% of range in trade direction
      • Engulfing the previous candle fully
      • Long wick rejection (wick > 50% of range)

  GATE 10: MOMENTUM-PAUSE-RETEST PATTERN (Aggressive setup, MPR module)
    Implemented in momentumPauseRetest.ts (findMomentumPauseSetup),
    replacing the old inline findMomentumPausePattern.
    H1 must show a specific sequence:
      • A strong directional candle (body ≥ 60% of range AND body
        ≥ 1.5× the average body of the 20 candles BEFORE it — the
        momentum candle is excluded from its own baseline)
      • Followed by a tight pause candle (range < 50% of the momentum
        candle's range) within 1-3 candles
      • Zero-range / structurally broken candles (NaN, high < low,
        close outside high/low) are rejected as feed errors
    When several setups qualify, the detector picks deterministically:
    freshest pause first, then tightest pause, then freshest momentum.
    If no valid setup exists → WAIT.
    This is the PRIMARY entry trigger — confluence alone is not enough.

  GATE 10b: STALENESS / DISTANCE GATE (inside the MPR scan)
    Current price (close of the in-progress H1 candle ≈ live bid)
    must be ≤ 0.75× ATR(14) from the pause midpoint. If price has
    run further, the retest is gone → SKIP. This is the wide-SL bug
    fix: the entry can never be staged far from the pause zone.

  GATE 11: CONSOLIDATION-WIDTH FILTER (inside the MPR scan)
    The pause candle's range must be ≤ 0.5× ATR(14).
    If the pause is wider → SKIP (no genuine tight setup formed).
    Configurable via MAX_CONSOL_ATR env var (default 0.5).
    /api/health reports the funnel: patternsDetected, passedFilter,
    blockedWide, blockedStale, noPattern.

  GATE 12: RISK:REWARD
    RR to TP1 must be ≥ 1:1.5 (lower than the old 1:2 minimum,
    because aggressive setups have tighter stops and faster targets).


------------------------------------------------------------------------
A3. STOP LOSS (Structure-Based)
------------------------------------------------------------------------

Entry is a LIMIT ORDER at the midpoint of the pause candle (the
retest level) — price must come back into the pause zone before the
position fills. Never a market entry at current price.

SL is placed beyond the pause candle extreme, NOT at a fixed ATR
distance.

  BUY:  SL = pause low − (0.15 × ATR)
  SELL: SL = pause high + (0.15 × ATR)

  Minimum floor: if SL distance < 0.3× ATR, widen to 0.3× ATR
  (prevents stops so tight they get hit by normal spread/noise).

All levels (entry, SL) are rounded to 5 decimals BEFORE the targets
are derived, so the published R:R (1.5R TP1, 2.5R TP2) is exact at
the quoted tick size. If rounding would ever collapse levels onto
each other (degenerate ATR vs precision), the setup is discarded.

By construction SL distance is bounded: pause ≤ 0.5× ATR means
mid-to-extreme ≤ 0.25× ATR, plus the 0.15× ATR buffer → SL is
0.15–0.4× ATR unless the 0.3× ATR floor widens it. Wide stops are
structurally impossible; there is no separate maximum cap.


------------------------------------------------------------------------
A4. TAKE PROFIT
------------------------------------------------------------------------

  TP1 = entry ± 1.5 × SL distance (closes entire position)
  TP2 = entry ± 2.5 × SL distance (reference level, not separately traded)
  TP3 = opposite range extreme (Draw on Liquidity reference)

When TP1 is hit, the trade closes as a WIN with the full R:R gained.
There is no partial closing (no "close 50% at TP1, 30% at TP2").
The entire position resolves at TP1 or SL.


------------------------------------------------------------------------
A5. CONFLUENCE SCORING (Determines Grade)
------------------------------------------------------------------------

After all gates pass, bonuses are counted for grading:

  +1  Weekly + Daily + H1 trends all aligned
  +1  Fresh POI (price never returned since creation)
  +1  POI found on H4 (higher timeframe zone)
  +1  Strong displacement (≥ 2× ATR)
  +1  Currently in London or NY Kill Zone
  +1  RSI extreme aligned (≤ 35 for BUY, ≥ 65 for SELL)
  +1  EMA20 > EMA50 confirms direction (on M15)

  Grade A+ = 5+ bonuses
  Grade A  = 3-4 bonuses
  Grade B  = 1-2 bonuses
  Grade C  = 0 bonuses (or any gate failed)

  Only Grade A+, A, or B trades are entered. C → WAIT.


------------------------------------------------------------------------
A6. BREAKEVEN LOGIC
------------------------------------------------------------------------

  When price moves 1× risk distance in favor (1:1 R:R):
    → SL is moved to the entry price
    → breakevenTriggered = true
    → If price subsequently hits the new SL (entry), trade closes at 0R

  This runs automatically on every cycle for every open trade.
  BE-triggered trades are exempt from the staleness check (see A7).


------------------------------------------------------------------------
A7. TRADE STALENESS (Safety Net)
------------------------------------------------------------------------

  If a trade has been open ≥ 12 hours AND:
    • Has NOT triggered breakeven, AND
    • Progress is below 0R (underwater)
  → Trade is closed at market price as a LOSS.

  This prevents trades from sitting open indefinitely with no
  progress. Designed to rarely trigger if SL/TP sizing is correct.

  Configurable via STALENESS_HOURS (default 12) and
  STALENESS_MIN_R (default 0.0).

  Logged at: GET /api/staleness-log


------------------------------------------------------------------------
A8. VOLATILITY-BASED COOLDOWN (After 20:00 GMT)
------------------------------------------------------------------------

  After 20:00 GMT, before force-closing any trade, the system checks
  whether the PAIR is still actively trading:

    1. Fetches 100 H1 candles for the pair
    2. Calculates current ATR(14) on recent candles
    3. Compares to same-hour baseline (average range of candles at
       the same hour ± 1 hour, from historical data)
    4. Ratio = current ATR / same-hour baseline

    If ratio < 0.65 (configurable) → pair is QUIET → close trade
    If ratio ≥ 0.65               → pair is ACTIVE → keep trade open

  This replaced the old "close everything at 20:00 GMT" rule.
  Gold and Silver (which stay active into the evening) are not
  force-closed if they're still moving.

  Configurable via EOD_VOLATILITY_THRESHOLD (default 0.65).
  Logged at: GET /api/volatility-log


------------------------------------------------------------------------
A9. SIGNAL EXPIRY
------------------------------------------------------------------------

  When a signal is generated (trade opened), it gets an expiresAt
  timestamp = now + 4 hours (configurable via SIGNAL_EXPIRY_HOURS).

  The /api/signals endpoint tags each signal as expired: true/false.
  The app UI shows expired signals at reduced opacity with ⏰ EXPIRED.

  Expired signals remain in the database for review — they are not
  deleted, just visually marked.


------------------------------------------------------------------------
A10. NEWS CHECK (Advisory Only)
------------------------------------------------------------------------

  The system fetches the Forex Factory economic calendar (XML feed)
  and checks for HIGH-impact events matching the pair's currencies
  today.

  If a high-impact event is found:
    → Flagged as advisory warning in the scan output
    → Does NOT block the trade (advisory, not a gate)

  The news feed is cached for 15 minutes to avoid rate limits.


------------------------------------------------------------------------
A11. CORRELATION CHECK
------------------------------------------------------------------------

  If two passing signals share a currency and have opposite bias
  (e.g., GBP/JPY BUY + GBP/USD SELL), both are flagged as a conflict.

  Both trades can still open — this is informational only, not a
  hard block.


------------------------------------------------------------------------
A12. DUPLICATE PREVENTION
------------------------------------------------------------------------

  Three layers prevent the duplicate-entry bug:

  1. Open-trade check: if pair has status "Open" → skip
  2. 30-minute post-close cooldown: no re-entry for 30 min after
     any close on that pair
  3. Same-setup smart check: after 30 min, if new signal is same
     direction + entry moved < 0.3% → block


------------------------------------------------------------------------
A13. TRADE TAGGING
------------------------------------------------------------------------

  Every trade is tagged with setupType:
    • "Aggressive" — opened under the momentum-pause + structure-SL
      logic (current system). Shows ⚡ AGG badge in UI.
    • "ATR" — opened under the old ATR-based SL logic (legacy trades
      still in the system from before the switch).

  The Performance tab separates these visually so you can compare.


------------------------------------------------------------------------
A14. DATA INTEGRITY GUARDS + HONEST CLOSE ACCOUNTING (2026-09-15)
------------------------------------------------------------------------

Background: on 2026-09-11 (NZD/USD) and 2026-09-14 (EUR/JPY) the
Capital.com candle feed served a series that ended days earlier while
the live-price endpoint returned current price. Every candle gate then
judged stale structure; the trade filled 56–84 pips off the planned
retest; the TP1 condition was already true at fill; the trade closed
seconds later tagged "WIN" with negative R. Three defenses now exist:

  1. DATA GUARD (per scan, in analyzePair)
     - H1/M15 candle feeds must be coherent with the live mid price
       (|last close − live mid| ≤ 3× ATR for H1 and M15, 5× ATR for H4).
     - The H1 series must not be older than 7 days.
     - Violation → scan rejected with a "[X] DATA GUARD" check line.
       (Cannot cross-check when the live fetch failed; the entry guard
       still protects fills in that case.)

  2. ENTRY GUARD (at trade open, in the background scanner)
     - A trade only opens with a verified live price, and only when the
       fill lies strictly between SL and TP1 on the correct sides for
       the direction. No market entry beyond TP1 or SL, ever.
     - Blocked entries are logged as ENTRY_BLOCKED in the scanner log.

  3. HONEST CLOSE ACCOUNTING (at SL/TP resolution)
     - rrGained is computed from the ACTUAL market price at close
       (checkPrice), not from the TP/SL level — includes slippage.
     - WIN/LOSS is classified by the sign of the actual P&L, not by
       which level triggered.
     - closePrice records the market price at close, not the level.
     - closeReason field on every close: TP1 | SL | BE | STALENESS |
       EOD_QUIET.
     - Note: SL closes now record actual slippage (e.g. −1.04R)
       instead of exactly −1.0R; breakeven stop-outs record the small
       real deviation instead of exactly 0.00R.

  CORRUPTED-TRADE POLICY: trades proven to run on corrupt data are
  flagged via dataQuality fields. They stay visible in history (⚠ badge)
  but are EXCLUDED from win-rate/R stats. As of 2026-09-16 ALL 28 pre-fix
  trades carry dataQuality "inverted-era" (every one was analyzed on
  time-inverted candles — see A16), including the two originally flagged
  "corrupted-stale-feed" (re-annotated: the feed was fresh, the arrays
  were reversed).

  CLEAN SAMPLE BOUNDARY: only trades OPENED after 2026-09-16T18:15:00Z
  (the inversion-fix deploy) count toward the clean MPR sample (exposed
  as `sample` in /api/performance/stats and cleanSampleSince in
  /api/health). Zero trades opened between the previous boundary and
  this one (the data guard blocked all scans), so nothing was lost.

  MANUAL CLOSE TOOL (2026-09-15, /api/admin/close-trade): closes an open
  trade at the live market price with the same accounting rules as the
  automated engine (spread-aware exit side, rrGained from actual market
  price, WIN/LOSS by P&L sign) and an audited closeReason + closeNote.
  Refuses to close without a verified live price. Used once, with user
  approval, to retire the pre-fix GBP/JPY legacy position (508-pip SL
  bug artifact, had frozen the pair from scanning for 11 days).


------------------------------------------------------------------------
A15. SIGNAL LIFECYCLE, LINKAGE & GATE FUNNEL (2026-09-15)
------------------------------------------------------------------------

What a SIGNAL actually is (documented truth, no decoration):
  - A signal is a LOG ENTRY, not an order. It is written whenever a
    scan passes all gates (any grade, including C) and is not a
    duplicate of the same pair+direction within 6 hours.
  - The trade (if any) opens INSTANTLY in the same 60-second cycle,
    at the LIVE bid/ask — Grade A+/A/B only, no open position on the
    pair, cooldown/same-setup checks passed, and now the entry guard.
  - "EXPIRED" on the Signals tab means ONLY "more than 4 hours since
    creation". The 4-hour window has NO mechanical effect. Nothing
    waits and nothing is lost to it.
  - Note: execution is an at-market entry near the zone (bounded by
    the MPR staleness gate ≤ 0.75× ATR), NOT a staged limit at the
    pause midpoint. That design gap is known and open.

Signal ↔ trade linkage (2026-09-15):
  - Every trade carries signalId (+ signalDeduped when the signal log
    was deduped against an earlier signal; the trade links to the
    earlier signal).
  - Every signal carries an outcome: ACTIVE | TRADED (with tradeId) |
    NOT_TRADED_GRADE_C | NOT_TRADED_SAME_SETUP | NOT_TRADED_ENTRY_GUARD
    | NOT_TRADED_OPEN_POSITION.
  - Historical trades were backfilled by pair+direction+timestamp
    (±10 s) via /api/admin/backfill-signal-links — deterministic, no
    price matching.

FILL-DRIFT TELEMETRY (2026-09-15, pure observability):
  - Every trade opened after this deploy carries fillDriftAtr: the signed
    distance between the ACTUAL fill and the planned retest entry, in ATR
    units. POSITIVE = favorable (BUY filled below plan / SELL filled above
    plan). NEGATIVE = adverse (fill beyond plan entry toward TP1).
  - No trading logic reads this field. It exists to inform the open design
    decision — whether to replace at-market entry with a staged limit
    order at the pause midpoint — at the 15-20 trade sample review.
  - /api/performance/stats exposes sample.fillDriftAvgAtr and
    sample.fillDriftSamples for the same purpose.


------------------------------------------------------------------------
A16. THE CANDLE-ARRAY INVERSION (2026-09-16) — ROOT CAUSE OF THE
     WIDE-SL SAGA
------------------------------------------------------------------------

Capital.com returns candle series in ASCENDING timestamp order (oldest
first; the last element is the current in-progress bar) — confirmed
against their API documentation and raw probes. The getCandles comment
claimed "newest first" (true for the old Twelve Data source, never true
for Capital.com), so analyzePair's five .reverse() calls (plus one in
checkVolatilityCooldown) INVERTED TIME for the entire analysis pipeline
from the day of the Capital.com migration:

  - "Most recent candle" references actually read the OLDEST bar
    (4-7 days back) of each window.
  - Trend, premium/discount, POI, M15 confirmation, and MPR pattern
    detection all analyzed 4-7-day-old structure as if current.
  - MPR's staleness gate compared the pause midpoint against a
    4-7-day-old "current price" — internally consistent old data.
  - Trades then entered at LIVE prices against old-data plans. When
    price revisited old levels the trades looked normal; when price
    trended away, entries were 50-110 pips off plan (the "wide-SL bug",
    the NZD/USD and EUR/JPY corrupted entries, and the contaminated
    25-trade sample were all this bug).
  - The 2026-09-15 data guard (comparing the analysis's "last candle"
    vs live) caught it within 26 minutes of market open — 100% of scans
    rejected, 16,440/16,440 over 35 hours — which is what exposed the
    inversion. The guard was never the problem; it was the alarm.

THE FIX (2026-09-16): the five reversals removed — h1Oldest/h4Oldest/
m15Oldest/dOldest/wOldest are now chronological, matching what every
downstream function always assumed. Additionally, getCandles SORTS by
timestamp — wire order is never trusted (one descending response was
observed in ~20 probes). Gate-funnel counters reset at this deploy (the
inverted-era rejections must not pollute post-fix statistics). Expected
post-fix behavior: dataGuard rejections ≈ 0 (true current bar vs live
drift is 0-2 pips), all trading gates finally evaluated on current
structure, and the first correctly-analyzed trades in the system's
history.

IMPORTANT CAVEAT — BACKTEST EVIDENCE: the local Python client had the
same inversion (get_candles_oldest_first returned newest-first). Every
backtest run through it — including the H1 analysis behind the 12h/0R
staleness rule and the SL/TP sizing sweep — was computed on inverted
data and is UNPROVEN (not necessarily wrong, but unverified). Rules
stay locked as-is per user decision; revalidation on correctly-ordered
data is a separate, future exercise.

Gate funnel telemetry (/api/health → gates):
  - Counters increment ONLY on background-scanner analyses, never on
    manual/API views, and persist in MongoDB (survive deploys and
    spin-downs). `since` marks when counting started.
  - blocked: spread, h1Trend, dailyAlign, pdZone, trendZoneMatch,
    poi_none, poi_dead, m15_noData, m15_noConfirm, mpr_noPattern,
    mpr_blockedWide, mpr_blockedStale, rr, insufficientData.
    (News is ADVISORY ONLY — it never blocks a scan; the "reduce size
    50%" message has no mechanism behind it.)
  - scannerSkips: sessionOff, eodLockout, openPosition, cooldown,
    sameSetup, gradeFilter, entryGuard.
  - dataGuard: h1Incoherent, m15Incoherent, h4Incoherent, h1StaleAge.

========================================================================
PART B — WHAT IS NOT IMPLEMENTED
========================================================================

The following are NOT enforced by the system. If you want these
behaviors, you must monitor and manage them yourself.

  ╔════════════════════════════════════════════════════════════════╗
  ║  B1. NO POSITION SIZING                                       ║
  ║  The system is paper trading only. There is no account balance,║
  ║  no lot size calculation, no risk-per-trade percentage.       ║
  ║  Every trade is virtual — 1R = full risk distance, regardless ║
  ║  of pair volatility or account size.                          ║
  ╚════════════════════════════════════════════════════════════════╝

  ╔════════════════════════════════════════════════════════════════╗
  ║  B2. NO DAILY TRADE LIMIT                                     ║
  ║  There is no "max 3 trades per day" cap. Trade frequency is   ║
  ║  purely a result of how often all gates align naturally.      ║
  ║  If 5 pairs qualify simultaneously, 5 trades open.            ║
  ╚════════════════════════════════════════════════════════════════╝

  ╔════════════════════════════════════════════════════════════════╗
  ║  B3. NO DAILY DRAWDOWN LIMIT                                  ║
  ║  There is no -2% daily stop. No consecutive-loss tracking.    ║
  ║  No "after 2 losses reduce size" logic. The scanner runs      ║
  ║  the same regardless of how many losses occurred today.       ║
  ╚════════════════════════════════════════════════════════════════╝

  ╔════════════════════════════════════════════════════════════════╗
  ║  B4. NO PARTIAL POSITION CLOSING                              ║
  ║  When TP1 is hit, the ENTIRE position closes. There is no     ║
  ║  "close 50% at TP1, trail the rest." TP2 and TP3 are          ║
  ║  reference levels only — they are not separately executed.    ║
  ╚════════════════════════════════════════════════════════════════╝

  ╔════════════════════════════════════════════════════════════════╗
  ║  B5. NEWS IS ADVISORY ONLY                                    ║
  ║  High-impact news events are flagged but do NOT block trades. ║
  ║  If NFP/CPI/FOMC is today, the system will still enter setups ║
  ║  during Kill Zones. You must check the calendar yourself      ║
  ║  if you want to avoid trading around news.                    ║
  ╚════════════════════════════════════════════════════════════════╝

  ╔════════════════════════════════════════════════════════════════╗
  ║  B6. CORRELATION IS INFORMATIONAL ONLY                        ║
  ║  If GBP/JPY BUY and GBP/USD SELL fire simultaneously, both    ║
  ║  trades open. The conflict is reported in the scan output but ║
  ║  not blocked. You must decide manually which to take.         ║
  ╚════════════════════════════════════════════════════════════════╝

  ╔════════════════════════════════════════════════════════════════╗
  ║  B7. NO TRAILING STOP                                         ║
  ║  After breakeven triggers, the SL stays at entry price.       ║
  ║  There is no trailing stop that locks in profit as price      ║
  ║  moves toward TP1. The trade either hits TP1 (win) or         ║
  ║  reverses to entry (0R breakeven).                            ║
  ╚════════════════════════════════════════════════════════════════╝
